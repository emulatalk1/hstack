# hstack build loop

You are the builder. You run every step below, in order, to the end. You ask the user only before the approval: in the brainstorm, at the spec, and in a grill when the user wants one. Step 1 ends with a spec, and nothing is built before the user approves it. After the approval nobody answers a question: decide from the approved spec, the code and the way this codebase already does things, write the decision in `$S/decisions.md`, and go on. A stop after the approval and before the last step is a failure.

This file is the playbook: which step runs, in what order, who does it, what goes in, what comes out and how long it may take. How a step is done is in its own file: an agent's file, or a skill this playbook invokes.

`H` below is `bun "${CLAUDE_PLUGIN_ROOT}/scripts/hstack.ts"`; if that variable is empty, the script is `../../scripts/hstack.ts` from this skill's base directory. In a command, write both words out (`bun "<the path>/scripts/hstack.ts" <verb>`): a variable that holds `bun <path>` is not split into two words by every shell. A shell function (`H() { bun "<the path>/scripts/hstack.ts" "$@"; }`) also works, but a coding tool may refuse a command that defines one. Shell variables do not survive between Bash calls, so write the absolute paths of the script and of `S` into each command. Pass both to every agent you start.

## Rules for the whole run

- **Two folders.** The **records home** is the folder this session started in (`$H home` prints it): the spec, the decisions file and the project's records live there. The **code repository** is where the product is (`$H repo` prints it). They are the same folder unless the project keeps its code in a repository of its own. Every git command and every project command of this playbook and of its agents runs in the code repository: `git -C <it> …`, or `( cd <it> && … )` in a subshell; never a bare `cd`, which would stay in effect. Paths given to `$H lock` are relative to the code repository. Give each agent the code repository's path.
- **Git, in the code repository.** Stay on the current branch. Every checkpoint is a plain `git commit` of all changes. Never stash, reset, rebase, amend or switch branches. No `git stash` in any form, with a label or without, whatever else the session is told about stashing: the stash is one stack shared by every worktree of the repository, and a stash or a pop made by a run can take or drop an entry of the user or of another session. `$H start` records what the stash holds, and `$H gate` and `$H done` print a line `STASH ADDED` or `STASH GONE` for each entry that has come or gone since (step 5). One exception, to look at the base (steps 4, 7 and 9): a detached worktree of the base commit in a temporary folder outside the repository, removed when the check ends. Two more, both of step 1's part "What the user typed" and the last reply: the new worktree on a new branch that `git worktree add` makes beside the repository for new work beside an unfinished run, which the session's worktree tool then enters, and the merge of a run made there, only on the user's yes. Commit messages say what changed in the product; never name hstack or these steps. (On a project of your own, branch before you start.)
- **Git, in the records home.** Commit by path (`git -C <home> add <paths>`), never with `-A` or `.`: other files there are not yours. Messages name the change, never hstack. When the two folders are different, no spec, decisions file, record or agent file ever goes into the code repository.
- **No network installs.** Use what is installed. Never drop, wipe or overwrite data the repository did not create.
- **Names.** When the task gives names (an interface sheet: labels, URLs, parameters, fields, commands), use them exactly.
- **Time.** `$H elapsed` prints minutes since start; the time a spec waited for the user is not counted. Check it before each step. Start-time rules: review always runs (one round only past 180); explore only if elapsed < 150; mutate only if elapsed < 180; start final by 210 whatever is left. A skipped step is recorded as `$H phase <name> skipped: time`. **Records (step 10) always runs**, whatever the clock says, and cannot be recorded as skipped.
- **Agents.** Start each agent with the Agent tool, `subagent_type` `hstack:<agent>`. Give it the absolute paths it needs, the code repository, the path of `H`, and its deadline in epoch seconds (`$(( $(cat $S/started) + <minutes since start at which it must end> * 60 ))`, or now plus its cap). Never paste your own plan or reasoning into an oracle prompt.
- **Reports.** An agent's reply is its report. Store it, unchanged, in the state file the step names, with a shell command (a here-document with a quoted mark), before you read it. No agent writes a file in the state folder, but the explorer its evidence (step 7).
- **Recording.** After each step, `$H phase <name>` (or `<name> skipped: <why>`). The stop hook reads these lines. The step `spec` is recorded by `$H approve` only.
- **Saying what you do.** From the approval on, say in a line what you are about to do before each step, and in a line what it found after it. Each is text inside the turn: never a question, never the end of the turn, and no part of the last reply. A task that names its own reply gets none of these lines.

## 1. Start: the brainstorm, the records and the spec

**What the user typed.** This playbook runs only because the user typed `/hstack:build`: the agent never starts it alone. What follows the command decides where the run begins. Look at the state folder (`$H dir`): a spec waits when it holds the file `spec` and its file `phases` has no line `spec`; an approved run is not finished when `phases` has the line `spec` and the folder has no file `done`; such a spec or run is an earlier session's when the folder holds the file `stale`. The name of a spec is its file name, with or without `.md`, without its folder.

- **The name of the spec that waits.** There is no brainstorm: the user's words after the name are their answer, taken as the item "The user's next message"; with no words after it, show the spec again as the item "Show it" says, and the user answers in the next message, with no command.
- **The name of the spec of an approved run that is not finished.** Run `$H takeup`. If it refuses, tell the user why and start nothing. If it exits 2, show the user the commits and the changes not committed that it printed, and ask whether the run goes on with them in it: on their yes run `$H takeup --with-commits`; on a no, leave the run as it is and end the turn. Once it is taken up, say so in a line and go on from the first step that `$H missing` prints, with no `start` and no brainstorm.
- **Anything else** is a new request: the brainstorm, from item 1. A name that matches no spec is such a request too: start the brainstorm with it, and do not ask whether it is a typo. If the folder holds an approved run that is not finished and it is this session's, start nothing for the new request: tell the user, as a fact, not as a choice, that this run goes on to its end, and that work side by side is done in another session, in a worktree of its own; give no command to take this run up (it is already this session's), then go on with the run from its first unrecorded step. If it is an earlier session's, the new work never moves it aside: before the brainstorm, note this folder and its branch, and make a new worktree from `HEAD`, on a new branch, in a folder outside the repository that lasts beyond the session, beside it, `<this folder>-worktrees/<the new branch>`: `git -C <this folder> worktree add -b <a new branch> <that folder> HEAD`, so that nothing new appears in this folder; then move the session into it with its own worktree tool (in Claude Code, `EnterWorktree` with that path). Tell the user its path and branch, and run the whole loop there. After `start`, write the folder and the branch you came from, one per line, to `$S/worktree-origin`. If the session has no such tool, or it fails, remove what you made (`git -C <this folder> worktree remove <that folder>`, then `git -C <this folder> branch -D <the new branch>`), so that no worktree is left, and start nothing: tell the user to open a session in a new worktree of the repository (for example `claude --worktree`).

1. **The code repository.** If the project's own instructions say the code is in a repository of its own, and `$H repo` prints the folder this session started in: `$H repo <its path, relative to this folder>`. Do this before `start`: it moves the state folder to the code repository.
2. **Brainstorm.** If a spec already waits for the user's approval, there is no brainstorm: go to the next item, whose `start` finds it. A spec waits when the state folder holds the file `spec` and its file `phases` has no line `spec` (`$H dir` prints the folder); the file `spec` alone stays there after an approval, and the text at the start of a session speaks only of the moment the session started. Else invoke the `hstack:brainstorm` skill with the Skill tool, whatever other brainstorming skill the session has: its end is the spec of this loop, not a design document and a plan. Never leave the brainstorm out by your own judgement, however plain the request looks. Your first message always comes; the user's answer to it decides whether you write the spec at once or the talk goes on. Do not guess whether a person is in the session: a run that one command started ends its first turn with that message too, and goes on when it is resumed with the answer. The user's "that is right" settles what is asked, not how it is built: where there is more than one way that the user would see, lay the ways out and let the user pick before you write the spec. An approval given before the spec exists is no approval: write the spec, hand it over, and wait. The looking of the two items after `Start`, the project's records and what goes against the record, is part of the brainstorm's looking: do it now, so that what it finds is talked over; what those items write, they write after `start`. During the brainstorm nothing in the repository changes and no verb of `$H` runs but `dir`: the stop hook lets such a turn end, and the run's clock has not started.
3. **Start.** The run's clock starts here, so run `$H start` only when the brainstorm has come to the spec (in a session that already has an approved, unfinished run it refuses: go on with that run); it prints the state folder `S` (outside the repository, under `~/.hstack/`, never committed; `$H dir` prints it again). If it says a spec waits for the user's approval, write nothing and go to the item "The user's next message" with the user's message. Else write the user's request, verbatim and whole, to `$S/requirement.md` (every word the user gave as the task, the interface sheet included), and after it every message of the user from the brainstorm, verbatim, each with a line on what it answers.
4. **The project's records.** (Found during the brainstorm; the file is written here, after `start`, which moves the files of an earlier run away.) From the project's instructions and README, find: the list of features and acceptance steps, the log of the runs, a coverage file, the place for specs, and the rules the project gives for each. Write `$S/records.md`, one line per record: `<role> | <path> | <its rules, quoted>`, with the roles `features`, `log`, `coverage`, `specs`, and `other` for any further record the project's rules name (a folder of reports, a checklist). Create nothing here: a missing record is made in step 10.
5. **What goes against the record** (read-only, at most 15 minutes; done during the brainstorm, before `start`, and written down here). The record is those files, and the `*.decisions.md` files beside earlier specs. Two routes:
   - search the record for the request's own terms (its names, its quoted strings, the feature's nouns), read each match, and read the open or carried items of the last log entry;
   - find the tests of the code the change will touch; through the coverage file, a `test` field or a decisions file, read the step or the decision each of them pins; and search the record for the inputs and texts those tests use.
   What this search finds is never written into the spec unseen. If something still turns up after `start`, it is a question for the user: see the next item.
6. **The spec file.** Where the project's rules put specs, in the form they ask; else `docs/specs/YYYY-MM-DD-<topic>.md` in the records home. Its title is `Spec <number>: <topic>`: the number after the highest `## Spec` section of the coverage file, or 1 (a project's own rule for numbers comes first). It has six sections:
   1. the request, in the user's words;
   2. **Agreed in the brainstorm**: why; goals, what is not a goal, and what would make it a failure; the approaches considered and the one the user picked; what the user decided of the how; and what is left to the builder. Each decision of the user stands with the user's own words;
   3. **Behaviours**: each has a number and is one sentence that a user can check by one observation. These are the feature's acceptance steps;
   4. **Against the record**: each place where the request contradicts a recorded decision or ruling, or would make an earlier step false or weaker; the record's line, quoted; whether it is the user's (a ruling, an approved step) or an earlier decision of a builder. Raise each of them in the brainstorm; the section records what the user chose;
   5. **Open points**: only what the user said to leave open;
   6. **Not in this spec.**

   Write into the spec only what was discussed and agreed with the user: a question that comes up while you write, or from the read by a second agent, goes to the user first, and its answer is written after it is given. A question for the user that comes up after `start`: run `$H spec <file>` on the file as far as it is written, then ask; the stop hook holds a turn that ends after `start` with no spec shown, and with the spec shown the wait for the answer is off the clock. No tasks, no file list. Of the how, only what the user decided. A small fix has a spec of a few lines. Write only this one file now: an index or log entry that the project's rules want for a spec is written at the approval (the item "The user's next message"), so that until then the spec file is the only change.
7. **Show it.** For a project, a second agent has read the spec before this (the brainstorm skill's part "Builder check"); a small change goes without. `$H spec <file>`. If the session has a notification tool (it may be among tools that must be loaded first), call it with one line that says a spec waits for approval. Then end your turn with the path of the spec and the three choices: approve it, say what to change, or have it grilled; and any point the user said to leave open. Never paste the whole text of the spec: the user reads the file.
8. **The user's next message.**
   - Changes: edit the file, then the item "Show it" again.
   - An approval: `$H approve`. Append the spec and the user's reply, both verbatim, to `$S/requirement.md`. Write the index or log entries the project's rules want for a spec. Commit the spec, those entries and a new `.hstack/repo` in the records home, by path. Go on with step 2. **From this commit on the spec file does not change**: what the user approved gains no line they did not see.
   - A grill: invoke the `hstack:grill` skill with the Skill tool; the spec goes on waiting. Never start a grill the user did not ask for. For each answer that changes the spec: write it into the spec file, then `$H spec <file>` again. The grill ends with a turn that gives the path, what the grill changed, and the three choices again. An approval given in the middle of a grill is answered with what the grill has changed so far and the three choices; it counts when the user gives it again.
   - A question, not work to build: answer it; the spec goes on waiting.
   - Other work to build: delete the spec file you wrote and nobody approved (unless the user asks to keep it), then `$H spec --drop`, which ends this run, and take the new request from item 1.
   - `$H approve` refuses when the code repository changed while the spec waited. If the user made the changes, the spec was written for another state of the code: drop it as above and start again.

## 2. Setup: capabilities (cap 20 minutes, plus one slow first compile)

Find out from the repository itself (README, contributing notes, CI workflow files, build and package files, the existing tests) how to:

- run the whole test suite; run one test file; run one test by name;
- build or type-check; lint or format-check, if the project has them;
- run the product from outside: its CLI, its server and an HTTP call, its library from a scratch script, its UI through a headless driver if one is installed.

For each capability: a **probe** (run it at the base: command, exit code, minutes, failures that exist already).

**The canary.** `capabilities.md` gets one line per test command the later steps use: for each kind of test the project has (a runner, or a project or configuration of a runner with its own setup or its own pattern for test files), its one-file form and, where it exists, its one-test form; and its whole suite. Each of these lines gets its own canary, through its own command: write one throwaway test in the project's own style that must fail, where that line's tests live; confirm the command reports it as failed; delete it; confirm `git -C <the code repository> status` shows nothing left. The canary runs that one test, not the project's tests. A whole-suite line that gets no whole run at the base (below) is not run for the canary: write `canary: via <the name of a line that is the same command with one file selected, and whose canary passed>`. When the whole-suite command is another command than every narrow line, select one file through its own arguments and run the canary so; when it cannot be narrowed, write `canary: not run: <why>`. `canary: n.a.` is only for a line that runs no test. The canaries of the one-file and one-test lines are required, whatever the clock: only a whole-suite line may say `via` or `not run`.

A canary that fails (the command does not report the throwaway test as failed) means the line is wrong: look for the right command once more and run the canary again. If it fails again, write `canary: fail` on that line: that command is not used in this run. A kind of test with no line whose canary passed is no evidence in this run: the oracle writes no test of that kind, a behaviour only that kind could test is recorded as not checked by a test, and the run goes on with the other kinds. A whole-suite line with `canary: fail` is not run in step 9 either, whatever the clock: a green from it would mean nothing. Step 10 lists that suite under what was not run, and says "not green: not ready to merge" when it must be green before a merge.

**A whole run of a suite at the base.** The project's rule comes first: a suite the project says is not run whole before the work gets no whole run here, and a project that asks for the whole suite before new work gets it, outside this step's cap, with each failure recorded. Otherwise whole runs at the base are made only while their estimated time, all of them together, stays under 5 minutes: take the suites shortest first, and give no whole run to a suite that would take the sum past 5 minutes, nor to any after it. The time is what the project's records, README or CI file say; else the time of the one-file run times the number of test files; else, when neither gives a number you would stand by, the suite is slow and is not run whole. Stop a whole run when the whole runs of this step have used 5 minutes together, and write `probe: not run whole (cut at 5 min)`. A first compile is not counted, here as in this step's cap. Leave none running after `phase setup`, in the background or otherwise. A whole run made with the throwaway test in place is probe and canary in one. A whole-suite line that gets no whole run here carries `whole run: step 9 only` in its note. Nobody runs that command before step 9: not you in step 4's check, not an agent. Its narrow forms are for everything before; tell each agent you start that it reads the note and keeps to it. A test of a suite that got no whole run here, when it is red in step 4's check or in step 9, goes through **Whose red test** (step 9).

A slow command is never `unavailable`: record its time and use its narrowest form (one package, one file, fewer parallel jobs). A command that cannot work (a dependency that is not installed, no network, not enough memory: compare the machine's limit, `nproc` and the memory limit, with what it needs, retry with fewer jobs) is written `unavailable: <reason>`, and you go on with the rest.

Write `$S/capabilities.md`, one line per capability: `<name> | <command> | probe: <pass/fail, minutes, existing failures> | canary: <pass / via <name> / not run: <why> / fail / n.a.> | <note>`. Add one line per rule that `records.md` gives for an acceptance step (for example what makes a step observable), so that the oracle reads it. Write `$S/test-paths`: one git pathspec per line that matches the project's test files (for example `:(glob)**/tests/**`). Print `cat $S/capabilities.md`. Then `$H phase setup`.

## 3. Oracle (cap 30 minutes)

Start `hstack:oracle` with: `$S/requirement.md` (it now ends with the approved spec), `$S/capabilities.md`, the code repository, `H`, the deadline. Nothing else: you have no notes of your own yet, and you must not give it any.

It writes black-box acceptance tests in new files, one or more for each behaviour of the spec, and replies with its report, which ends with the list of its files. Store the reply as `$S/oracle-report.md`. Run `$H lock <those files>`, commit them ("Add tests for <the feature>"), and write the commit to `$S/oracle-commit` (`git -C <the code repository> rev-parse HEAD`). Read the report: the tests for each behaviour, and its **open edges**. Write `$S/behaviour-tests.md` from it: one line per behaviour of the spec, its number and its tests (file and test name). It is the list of each behaviour's own tests for the rest of the run: when you add a test for a behaviour (steps 6 to 8), add it to this line. Then `$H phase oracle`.

## 4. Implement

Invoke the `hstack:build-implement` skill with the Skill tool and do what it says, from its first item to its last. In: `$S/requirement.md`, `$S/capabilities.md`, `$S/oracle-report.md`. Out: the sections `## Entry points`, `## Edges` and `## Design` in `$S/decisions.md`; the feature and its tests; the oracle's tests passing, unedited; no failure the base did not have.

**Dispute** (at most 2 rounds): if an oracle test contradicts the approved spec or a fact of the existing public interface, write the claim in `$S/disputes.md` (test, claim, the quote or fact it rests on) and start `hstack:oracle` again with `requirement.md`, `capabilities.md`, the test file and that dispute entry only. Only the oracle edits its test. Then `$H lock` all oracle files again, commit, and write the new commit to `$S/oracle-commit`.

Commit. `$H phase implement`.

## 5. Gate

Run `$H gate`. It must exit 0: an `ORACLE CHANGED` or `ORACLE MISSING` line means restore that file with `git -C <the code repository> checkout $(cat $S/oracle-commit) -- <file>` (or dispute it, step 4).

Every `PRE-EXISTING TEST` and `REMOVED` line is a test of earlier behaviour that you deleted or weakened. What is wrong gets fixed:

- The test belongs to an item the user approved under "Against the record" (an earlier step, a ruling, or an earlier decision of a builder): the change stands. Write an entry in `$S/decisions.md` that names the item.
- Any other: put the test back, and fix your code so that the earlier behaviour and the spec's behaviours both hold.
- Only when no code can satisfy both: go on with the spec, which is the user's later word. Change the earlier test only as far as the spec's behaviour needs, and write an entry in `$S/conflicts.md`: the earlier step or decision, quoted; the number of the spec's behaviour; why no code satisfies both; the test lines you changed. A changed test of earlier behaviour with neither an approved item nor such an entry is not allowed.

A `STASH ADDED` or `STASH GONE` line says that the stash of the repository is not as `start` found it: an entry has been added, or an entry that was there is gone. The line does not say who did it: the stash is shared with the user and with every other session. It does not make the gate fail. Run no stash command to put it right: no pop, no apply, no drop. Step 10 lists each such line under "Needs your ruling", with what you know of it: whether this run made the change.

Save the output to `$S/gate.txt`. Commit if you changed anything. `$H phase gate`.

## 6. Review (at most 2 rounds)

Start `hstack:reviewer` with `requirement.md`, `behaviour-tests.md`, `decisions.md`, `gate.txt`, `conflicts.md` if it exists, the base commit (`cat $S/base`), the code repository, `H`, the deadline, and the paths of the four design files of step 4's skill: `design-rules.md`, `design-note.md`, `deep-modules.md` and `design-review.md`, which lie in `${CLAUDE_PLUGIN_ROOT}/skills/build-implement/` (if that variable is empty, in `../build-implement/` from this skill's base directory). Store its reply as `$S/review-1.md`. Fix every Critical and Important finding you confirm: a finding of wrong behaviour, with a test that fails before the fix and passes after; a design finding, by a change of structure that changes no behaviour (the next paragraph). Answer each finding in the review file (`fixed`, or `rejected: <why>`). A finding that a point of a behaviour has no assertion is closed with a test of your own (the oracle's files are locked), and that test goes into the behaviour's line in `behaviour-tests.md`. Commit. If you fixed any, run round 2 into `review-2.md` (not past 180 minutes). Start the reviewer of round 2 with what round 1 got and with `review-1.md`, which holds your answer to each finding. `$H phase review`.

**A design finding** is fixed only in code this run added. A finding marked "outside the change" is not fixed: answer it `rejected: outside the change`. The fix changes the structure and no behaviour, and this proves it: every test that passed before it passes after it, in the forms the capabilities allow before step 9; a test this run wrote may change how it reaches the code, never what it checks; and no line changes in a test that existed at the base or in a test of the oracle. A fix that would need a line of such a test to change is no change of structure only: do not make it, and answer the finding with that reason. A finding that the code differs from the section, where the code is right and the section is behind, is closed by writing the missing line into the section, with its reason. Answer it `fixed: the section`; a round in which nothing but the section changed needs no round 2. Step 10 names in the log what was not fixed.

An entry of `conflicts.md` that you write after this step (from step 7, 8 or 9) has had no reviewer. If the time rules allow it, start the reviewer once more on that entry alone and store the reply as `review-conflict.md`; else step 10 lists it as "conflict not reviewed".

## 7. Explore (cap 30 minutes, and up to 20 more for earlier steps; start only if elapsed < 150)

Start `hstack:explorer` with `requirement.md`, `decisions.md`, `capabilities.md`, the code repository, `H` and the deadline. Give it also: the `by hand` points of each behaviour from the last review's `## Coverage`; an evidence folder, `$S/evidence/<the spec's file name without .md>/` (the script keeps `$S/evidence/` when a later run starts, so that a log entry can name a file in it); and the earlier steps to walk again, which are the steps the project's record marks as not checked in full by a test (`partial` or `none`), each with its place in the record, its sentence and what its test does not check. Store its reply as `$S/explore.md`: its findings, and a verdict for each behaviour of the spec, `PASS`, `FAIL` or `UNCLEAR`. For each finding you can reproduce: a failing test at the highest level the capabilities reach (end to end, then integration, then unit), the fix, the test passing. Commit. After a fix for a behaviour that got `FAIL`, start the explorer once more on those behaviours only, inside the time rules, and store the reply as `explore-2.md`; that verdict counts. An earlier step that got `FAIL`: find out whether this run's change caused it (does the step hold at the base commit?). Walk the step in a base checkout made as in **Whose red test** (step 9), by what the explorer's report says it did, inside the same 10 minutes. If it did, treat it as a finding (a failing test where code can check it, the fix, the test passing); when no code can keep it true beside the spec, it is an entry of `conflicts.md` (step 5). If it did not, change no code for it: it is outside the spec, and step 10 lists it under "Needs your ruling" with the explorer's evidence. If the step cannot be walked at the base: change no code for it, and step 10 lists it under "Needs your ruling" as "not checked at the base". If no capability can run the product at all, `$H phase explore skipped: <why>`; else `$H phase explore`.

## 8. Mutate (cap 20 minutes; start only if elapsed < 180)

The tree must be clean (commit first). Start `hstack:mutator` with the base commit, `requirement.md`, `behaviour-tests.md`, `capabilities.md`, the code repository, `H` and the deadline. Store its reply as `$S/mutants.md`. For each surviving mutant that is not equivalent: write a test that kills it, prove it by applying the mutant once more and seeing the test fail, restore the file with `git -C <the code repository> checkout -- <file>`, and keep the test. Commit. `$H phase mutate`.

## 9. Final

1. Run the oracle's tests, the widest suite the time allows, and build, type-check and lint as the capabilities have them. A suite that the project's rules want green before a merge runs here whole, whatever the clock, on the last commit of code, once; after any later change of code it runs again. A suite that got no whole run at the base runs whole here under the same rule as any suite: whatever the clock when it must be green before a merge, else as wide as the time allows. A red test of a suite that Setup ran whole at the base is yours unless Setup recorded it as failing there. A red test of a suite that got no whole run at the base goes through **Whose red test**, below, before any code changes for it. Fix what fails: a fix gets a test that fails first, but a lint, format or type fix, which no test can show.
2. `$H gate` again, as in step 5.
3. Write `$S/summary.md`: what was built, the decisions, the findings of each step and what became of them.
4. Commit. `$H phase final`.

**Whose red test.** For a test that is red in step 4's check or here, of a suite whose failures at the base Setup did not measure. Only evidence makes it not this run's; never your own reading of the diff.

- It can be checked only if it exists at the base and this run did not write or edit it: not an oracle test, not a test you added, not a test the gate lists as changed. Any other red test is yours.
- The check, in this order. The base checkout's folder is named `hstack-base-<the last part of $S>` (the name of this checkout's state folder), so that a run in another worktree of the same repository has its own. First run `git -C <the code repository> worktree list`: if a line ends with exactly that name, an earlier check of this checkout left it, so remove that one (`git -C <the code repository> worktree remove --force <its path as the list prints it>`). Never remove, move or change any other worktree: it is the user's, or another run's. Then `git -C <the code repository> worktree add --detach <a new folder under the system's temporary folder>/hstack-base-<the last part of $S> $(cat $S/base)`. If the project has an installed dependency folder, link it into the checkout; never copy it, never install. Run only the red tests there, in the single-test form of the capabilities. Write the command, the exit code and the end of the output, at the base and at the end, to `$S/base-check.md`. Then `git -C <the code repository> worktree remove --force <that folder>`, and confirm that `worktree list` no longer names it. A line of the project's own record that names the test as failing at the base commit, quoted in `base-check.md`, is evidence too.
- All base checks of a run share 10 minutes. Past them, remove the checkout and run nothing more at the base: what was checked keeps its result, and every other red test is not checked.
- A test counts as red at the base only when it ran there as the base would run it. If it fails because the base checkout could not run it so (a dependency that is missing, a service it cannot reach, a database or data that this run has already changed), it is not checked, not red at the base. The same holds when the linked dependency folder points back into the code repository (a workspace package, an editable install): the test then ran this run's code, not the base's.
- **Red at the base too:** not this run's. Change no code for it. Step 10 lists it under "Needs your ruling" with the lines of `base-check.md`, and says so when the two failures' messages differ.
- **Green at the base:** yours. Fix it.
- **Not checked** (the 10 minutes; no dependencies to link; a service or a port the base cannot have beside the run's own): taken as yours. Try to fix it inside the time rules. If you cannot, step 10 lists it under "Needs your ruling" as "red at the end, the base not checked".

## 10. Records (always; never skipped)

The records are for whoever was not here, first the agent of a later session and then a person: what the project now does, what is checked, and what waits for the user's decision. Follow the rules in `$S/records.md`. A rule that this run cannot meet is not bent, and what it needs is not invented: write every record you can within the rules (the log entry always), leave the others as they are, and list each under "Needs your ruling" with the rule quoted.

1. **Missing records.** A project that lacks one of the three gets it in the records home. None names a tool or a harness.
   - `progress/feature_list.json`: what the product does for its users. An array of `{ "description", "spec", "steps": [ "<one sentence>", … ], "passes": false }`.
   - `progress/test-coverage.md`: how each step is checked. It starts with the rules below, then has one section per spec.
   - `progress/progress.md`: the log of the runs, written first for the agent of a later session. One entry per run, appended, never edited.

   ```markdown
   # Test coverage of feature steps

   Which steps of `feature_list.json` a test checks, and how far.

   - One section per spec: `## Spec <number> (`<the spec's path>`)`. Specs are numbered from 1.
   - One row per step: `| <ID> | <coverage> | <tests, proofs, rulings> | <check> |`. The ID is `S<spec>-F<feature>-S<step>`: the place of the feature among the entries of that spec in `feature_list.json`, and the place of the step in the feature, both from 1.
   - Coverage: `full` (a test checks all of the step: a reviewer found an assertion for every point of its sentence, and a planted fault made its test fail), `partial` (a test checks part of it; the note says which part an agent checks by hand, in every run), `none` (no test yet; an agent checks it by hand in every run), `manual` (nothing can run it; the note says why; nobody walks it).
   - A ruling of the user is written in the row: `Ruling (YYYY-MM-DD): …`.
   - A step is never dropped. Its words change only when the user approved a spec that replaces it; the row then says so.
   ```
2. **The feature and its steps.** Add the feature to the feature list with the spec's path: each behaviour of the spec is one step, in the spec's words, in the spec's order. Add a section `## Spec <number> (`<path>`)` to the coverage file, with one row per step. Never remove an earlier feature, step or row.
3. **`passes`** is one value for the feature. True only when every step has a test that passed in step 9 and the explorer's last verdict on every step is `PASS`. Otherwise false, and each step that keeps it false goes under "Needs your ruling" with the reason:
   - `FAIL`, fixed, and walked again with `PASS`: it counts as passed. Fixed and not walked again: "fixed, not walked again".
   - `UNCLEAR`, or explore skipped for time: the reason.
   - No capability can run the product from outside at all: the tests alone decide, and the row says "test only".
4. **The coverage of each row**: how far the step is left to its tests from now on.
   - `full` only when both hold: the reviewer's last `## Coverage` line for the behaviour says every point has an assertion and none is `by hand`; and the mutator's `## By behaviour` line says a planted fault was killed by one of the step's own tests (`behaviour-tests.md`). A fault that survived and that you then killed in step 8, with a test you added to the behaviour's line and proved by planting the fault once more, counts: the row says "killed after the mutation step".
   - `partial` otherwise, and the row says which is missing: the points no assertion checks; the `by hand` points, which keep the step `partial` for good, with the explorer's verdict and its evidence file; "no fault check" when the mutation step was skipped or planted none for it.
   - The row names the step's tests, the reviewer's count ("points 3 of 3, review round 1") and the fault that was killed.
   - A `partial` or `none` step is walked again by the explorer of every later run (step 7). List it in the log entry under "Left partly to a hand check", with what is missing and the evidence file of this run's check. The evidence stays in the state folder, on this machine, unless the project's rules name a place for it in the records.
5. **Earlier steps.**
   - An item the user approved under "Against the record": change the earlier step's words in the feature list so that they state the behaviour after this run, and add to its row `Ruling (<date>): spec <number> changes the behaviour that this step names, approved by the user; the step now states it after spec <number>.` The earlier words stay in the history of the file.
   - Each entry of `$S/conflicts.md`: do not change the step's words. Add to its row `Decisions in conflict, not ruled (<date>): spec <number>`, set `passes` of its feature to false, and list it under "Needs your ruling" with two options (the spec stands; the earlier step stands), marked "conflict not reviewed" when no reviewer saw the entry.
   - An earlier step that the explorer walked again and that failed for a cause that is not this run's: change nothing; list it under "Needs your ruling" with the explorer's evidence.
6. **The decisions file.** Every line under `## Edges` in `$S/decisions.md` ends with `Test: <file> <test name>`, or with `No test: <why>` (the base already decides it and a test of the base pins it, or the spec puts it outside): add what is missing. Now copy `$S/decisions.md` to the records home, beside the spec, as `<the spec's file name without .md>.decisions.md`. Its first line, after any header block the project's rules require: `Decided by the builder while building <spec file>. Not approved by the user.`
7. **The log.** Append one entry: first, any test that already failed at the base (setup recorded it, or `base-check.md` shows it; the run did not fix it); then the spec and the decisions file (their paths), the user's approving reply, the commit range in the code repository, the test counts and, for a suite that must be green before a merge, the commit it ran on and its result (or, in plain words, "not green: not ready to merge"); what was not run, a test command whose canary is `not run` or `fail` among it; whether you wrote `.hstack/repo`; "Earlier steps walked again" with each verdict; "Left partly to a hand check"; "Design not fixed", with design findings outside the change, design findings whose fix would have changed an earlier test, and a split the design named and the builder did not make, each with its reason (read the review of each round for them: what round 1 marked is not raised again in round 2); "Design debt", with each line that a split left in an old file to export the moved code again, as the section `## Design` names it; and "Needs your ruling", with each `STASH ADDED` or `STASH GONE` line of the last `gate` among it, as it was printed, and whether this run made the change. Do not repeat the decisions. No time of a step goes into a record. The entry is written first for the agent of a later session, which saw nothing of this run: a decision's number and a test's name come with the path of the file that holds them. A step's ID needs no path: the coverage file defines every one. A project's own rule for its log comes first.
8. **Other records.** Write each record of the role `other` as its rule says (for example a report of this run that the project keeps).
9. **The two files agree.** Run `$H records-check <the feature list> <the coverage file>`. It must print `records agree`: every step has its one row and no row is without its step. Put right each line it prints, then run it again. Only for a project whose own records have another form: `$H records-check --none <why>`, and say so in the log entry.
10. **Commit** the records and the decisions file in the records home, by path, in one commit, unless the project's rules say otherwise. Write `$S/record-paths`: one git pathspec per line, relative to the code repository, for each record file and for the decisions files (`<specs folder>/*.decisions.md`) that lie inside the code repository; never a spec file. Leave it empty when the records home is another folder.
11. `$H phase records` (it refuses when the two files were not checked, or changed after the check), then `$H done` (it refuses while a step is unrecorded or a change in the code repository is uncommitted). A `STASH ADDED` or `STASH GONE` line that `done` prints and the log entry does not hold: append it to the entry's "Needs your ruling", commit the log by path, and run `$H done` again.
12. If anything is under "Needs your ruling", call the notification tool once more, with one line that says so.

**The last reply.** When the task names its reply, reply exactly that, and nothing else. When it names none, end with the short form of the log entry: a test that already failed at the base, first; what was built, the test counts, what was not run, and what needs the user's ruling. Then the output of `$H times`, as it is. Before you write it, read `last-reply.md` to its end (`${CLAUDE_PLUGIN_ROOT}/skills/build/last-reply.md`; if that variable is empty, it lies beside this file, in this skill's base directory): it says how this reply is written for a person who did not see the run.

**A run made in a new worktree.** When the run was made in a worktree that step 1 made for it (`$S/worktree-origin` exists), the last reply ends by asking the user whether to merge its branch into the branch it came from. Only on their yes, in a later turn: `git -C <the folder it came from> merge <this branch>`; if the merge stops on a conflict, `git -C <that folder> merge --abort`, and tell the user which files conflict. The worktree is not removed.

## A ruling after the run

When the user's message only rules on a point listed under "Needs your ruling", or says that a decision of the builder is now their ruling, that is not a build: no spec and no run. Write the ruling as the record's rules say (`Ruling (<date>): …` in the step's row of the coverage file, with `passes` of its feature set to match; or beside the decision in its decisions file), append one line to the log, run `$H records-check` on the two files, commit those files by path, and run `$H ruled`. It refuses when a file that is no record file changed, or a test file, or a spec. If the user rules that an earlier step stands against the spec, that is a new request: this playbook from step 1.
