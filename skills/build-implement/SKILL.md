# hstack build-implement: step 4 of the build loop

You are here from step 4 of `hstack:build`: that loop gave you `H` and `S`, and its steps 1 to 3 ran in this session. If that is not so (you came here straight from a request to build, change or fix something), do nothing here and invoke `hstack:build`, which starts the run. If it is so, run `$H missing`: its first word must be `implement`. If it is another step, go back to that step in the loop; never run `$H start` again in this run. Every command below runs in the code repository, as the loop's rule of the two folders says.

Do the items below in order, then go back to the loop for the commit and `$H phase implement`.

1. **Read** the code the approved spec touches and the neighbouring features that do similar things.
2. **Entry points and edges.** Before any line of product code, write two sections into `$S/decisions.md`. `## Entry points`: every way the feature is reached (each page, endpoint, command, public function, import or export path, serializer, setting). `## Edges`: each open edge from the oracle report and every other edge you see (empty, missing, invalid, boundary values, errors, permissions, existing data, repeated actions, ordering, other entry points), each with a decision that cites the approved spec or the existing code it follows. Decide an edge the way this codebase already decides the same case. The behaviours are the approved spec's, in `$S/requirement.md`, under their numbers: do not write them again. End each edge's line with `Test: <file> <test name>` when the edge gets its test (item 4), or with `No test: <why>` when it gets none (the base already decides it, or the spec puts it outside): the file is kept beside the spec, and a later run finds a decision from its test.
3. **The test rules.** Read `tdd.md` and `writing-good-tests.md` in this skill's base directory, both to the end. From here to the end of the run they are the rules for every test and every line of product code you write.
4. **Implement,** in the style of the neighbouring code, by the cycle of the test rules, one decided edge or rule per cycle: write one test where the project's test command finds it, run it and see it fail on the missing behaviour, write the code for that one test, run it and see it pass. Only then write the next test: never several tests before their code. A next test that passes at once, because code you already wrote settles its edge, is kept only as the test rules say: break that code, see the test fail, undo that one edit by hand (your code is not committed yet). A change to what the product does after its test passes (an output, a message, an exit code) is a new cycle and starts with a test that fails; the cycle's refactor step changes none of these. Run tests in their single-file or single-target form from the capabilities.
5. **The oracle's tests.** Make them pass **without editing them**. If one contradicts the approved spec or a fact of the existing public interface, use the dispute rule of step 4 in the loop.
6. **Check.** Run the tests near the change, then the widest suite the time allows, then build, type-check and lint as the capabilities have them. No failure the base did not have.
