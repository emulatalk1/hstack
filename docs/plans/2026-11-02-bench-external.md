# External Task Selection Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prereg section 12 step 4 done: 24 external tasks (8 per stack) chosen by the section 4.2 rule from a candidate list that was committed before any task was checked, each with what step 5 needs (repo, base and end commits, the issue text as of the PR's opening, a container recipe that runs its tests).

**Architecture:** One CLI, `bench/ext.mjs`, with three commands. `list` enumerates a repo universe on GitHub (search sliced under the 1000-result cap, then each repo's merged PRs through GraphQL), applies the static criteria and writes one sorted list per stack. `check` takes one candidate: base commit, issue snapshot, a container recipe written by a sealed agent from the files at the base, images at the base and the end, runs the PR's test files at the base (copied into the container) and at the end, and counts fail-to-pass tests, printing only counts. `walk` calls `check` down each sorted list until the stack has 8 tasks. The stack definitions (languages, marker files, test-path patterns) are data in `<data>/ext/groups.json`, so `bench/` names no stack.

**Tech Stack:** Bun 1.4.4+, `bun:test`, `gh` (logged in as emulatalk1; `gh api` and `gh api graphql`), git (blobless clones), Docker 29.9 on this arm64 Mac, the `claude` CLI 2.1.310 through `bench/sealed-agent.mjs`.

**Spec:** `docs/plans/2026-10-27-benchmark-prereg.md` sections 4.2, 7.1, 7.3, 10.2, 12 (steps 4, 5, 11), 13 (item 4); the tools as built: `bench/README.md`.

## Rulings section 4.2 leaves open (Task 1 registers them in the prereg before any enumeration)

Rulings 1 and 13 were decided by the user on 2026-11-02; the rest are proposed by this plan.

1. **Stacks (the user chose them on 2026-11-02).** S1 web app with a database = a repo whose GitHub primary language is Python with a Django app (`manage.py` that names `DJANGO_SETTINGS_MODULE`, at the root or in a folder one level below), or Ruby with a Rails app (`config/application.rb` and `bin/rails` at the root; `config/database.yml` is often gitignored, so it is not required). Not Next.js: `real-estate` is Next.js and S2 is TypeScript, so S1 would share a language and toolchain with both. S2 desktop app = primary language TypeScript, JavaScript, Vue or Svelte with an Electron app (a `package.json` whose text has `"electron":` and, in the same folder, a packaging config: `electron-builder.*`, `forge.config.*`, `electron.vite.config.*`, or `"build": {` / `"forge"` in that `package.json`; the root or a folder one level below). No Tauri: it needs Rust and system web libraries in the container, and its Rust tests sit inside source files. S3 CLI or library = primary language Rust with `Cargo.toml` at the root and no `src-tauri/` folder. Markers whose path has a folder in it (Rails) are looked up from the root only. The language sets are disjoint, so a repo is in at most one stack. A Rust web server is not excluded (no mechanical test separates it from a CLI or library); it is a known limit.
1a. **Rust tests.** Rust unit tests usually sit inside the source file (`#[test]` in `src/*.rs`); copying such a file from the end to the base would copy the fix with it. So for S3 only files under a `tests/` folder (integration tests, which for a CLI run the real program) are test files; a PR whose test changes are all inline is `no test file`.
2. **Repo universe.** Per stack, every repo with stars ≥ 1000, `pushedAt` ≥ 2026-07-01 ("active after 2026-07-01"), `createdAt` < 2026-01-01 (brownfield: at least six months of history before the first eligible PR), not a fork, not archived, not a mirror, `licenseInfo.spdxId` in the OSI list of `groups.json` (`NOASSERTION` and none are out), and not used in hstack. Counts on 2026-11-02 for these qualifiers before the marker check: Python 4617, Ruby 485, TypeScript 3599, JavaScript 2116, Rust 1527 (Vue and Svelte not counted yet). Search is sliced by stars range until each slice reports under 1000 results.
3. **Widening.** If a stack's list is exhausted before it has 8 tasks, a second tier (stars 500 to 999, same rules) is enumerated, sorted by the same key and committed before any of it is checked, and walked after tier 1. Still short: stop and ask the user. N never drops below 24.
4. **Snapshot window.** PRs created from 2026-07-01T00:00:00Z and merged before 2026-11-01T00:00:00Z into the default branch. The raw API responses are kept and hashed; a rerun of `list` later will not reproduce the list exactly (merges land daily, search ranking moves), so the committed list and the raw responses are the record.
5. **"Links the issue".** `closingIssuesReferences` has exactly one issue, in the same repo, created from 2026-07-01 and before the PR's `createdAt`. More than one, another repo, or an earlier issue: out, with the reason.
6. **Tests.** The PR changes at least one file matching the stack's test-path patterns and at least one other file that is not Markdown or under `docs/`; a PR with more than 100 changed files is out (its file list cannot be read whole in one page, and it is not PR-sized). PR author of type `Bot` is out.
7. **Sort key.** `sha256("<owner>/<repo>#<n> hstack-bench-2026-10-27")`, the id lowercased, one space before the seed, hex compared ascending; one list per stack; tier 2 after tier 1. Test vectors: `octocat/hello-world#42` → `bea5910fe308bac50ac3fe749d703078d7b3e8b3092710af42634f494c6a8c19`, `octocat/hello-world#7` → `3215ff12f22f2e4479f5b9d3b6720760bffad246a8bf123b1ece0900606d9359`.
8. **Static then runtime, in sort order.** Criteria that need a run (runnable in a container, a fail-to-pass test) are checked by walking the committed list from the top; the walk stops for a stack at 8 accepted tasks. The sort key does not depend on any criterion, so filtering everything first and walking in order give the same sample; rows below the stop are recorded as `not checked`. At most 2 tasks per repo: a candidate of a repo that already has 2 accepted tasks is `repo cap`, not checked; the cap is recomputed from the accepted tasks each time, so a cap freed later (ruling 14) reopens those rows. A failure of the tool itself (clone, docker daemon, a parse) is `error`, never an out reason: the row is checked again, and the walk stops after 2 errors in a row.
9. **Base and end.** End = the PR's `mergeCommit`. Base = its first parent when it has two parents (merge), or when the PR has one commit, or when `git diff --name-only <end>^1 <end>` equals the PR's file list (squash). Otherwise (a rebase merge of several commits) out: its parent would hold part of the PR, and 7.1 needs a clean known-bad version.
10. **Runnable and fail-to-pass.** A recipe (image, setup at build time with network, a test script that runs given test files with no network and writes JUnit) is written by a sealed agent that sees only the repo's files at the base (no `.git`), at most 3 rounds per repo, plus 1 round for each further task of the repo. The test files are the PR's changed files matching the test patterns that exist at the end. Fail-to-pass = a test case (`classname` + `name`) that passes in both of two runs at the end and fails, errors or is missing in one run of a container of the base image with the PR's test files copied in (deletions applied). "Runnable" means these tests run; whether an S1 or S2 app can also be served in the container is checked in step 5, and a task that cannot is dropped there (ruling 14). Limits: image build 45 minutes, test run 30 minutes. A failed end-image build gets no recipe round (its log is after the PR and stays sealed): the candidate is `end build failed`. The recipe may name `linux/amd64` (run under emulation) when a dependency has no arm64 build. Out reasons, in order: `rebase merge of several commits`, `recipe failed`, `end build failed`, `PR tests do not pass at end`, `no fail-to-pass test`.
11. **Requirement text.** The issue's title and body as they stood at the PR's `createdAt`: the body from `userContentEdits` (the last edit before that time), the title from `RenamedTitleEvent`s after that time undone. When the body was edited after the PR opened and the history does not give the earlier text, the task stays and is flagged `edit-history: unverified`. No comment is kept.
12. **Used in hstack.** A repo hstack ran as a project (built, tested or replayed): `real-estate` (private), the `daily-routine` app (private), `fixtures/electron` (local). None is public, so "at least 6 of the 8 repos never used in hstack" holds for every sample; the check is recorded. The 8 tasks of a stack come from at least 4 repos (at most 2 each); the prereg's "6 of the 8 repos" is read as "all but at most 2 of the stack's repos".
13. **Cold-setup repo (the user agreed on 2026-11-02).** Per stack, the sampled repo whose best-ranked task ranks lowest (the last repo to enter the stack's sample). The first repos of the list are taken by the canary (7.3, first 2 per stack) and the trial run (step 11, which runs H on them before the plugin is locked), so they cannot stay unseen. Nobody designing the plugin opens the cold-setup repos.
14. **Later needs.** A sampled task dropped in step 5 (for example no valid oracle check), or more tasks needed by the N rule of 10.2, are taken by continuing the same walk on the same committed list: a dropped task frees its repo's cap, so that repo's `repo cap` rows are examined again in sort order before the walk goes on below where it stopped.
15. **Model cutoff.** 2026-07-01 is after the June 2026 cutoff of the configured model; the cutoffs of every model are recorded at the lock of step 12. A model with a later cutoff then is a prereg change at that time.

## Known limits

- The universe is GitHub's primary-language and star view at one date; a Django or Electron app whose primary language is HTML or C++ is not in it. A Rust web server counts as S3.
- One run at base-plus-tests and two at the end: a test that is flaky at the base can still be counted; step 5's validation reruns every check. A PR test file that does not compile at the base makes every case of its package or file "missing", so the fail-to-pass count can be high; eligibility (at least one) is unaffected.
- S3 counts only integration tests under `tests/` (ruling 1a), so crates tested only inline are out; S3 leans toward CLIs and crates with integration tests. Rust builds are slow; a big workspace can hit the 45-minute build or 30-minute test limit and end `recipe failed`.
- "Runnable" is checked on the tests only; an app that cannot be served in a container is found in step 5 and replaced by ruling 14.
- The recipe agent reads repo files that may carry instructions (a `CLAUDE.md`, an `AGENTS.md`); it has only read tools and its reply is data, so the damage is a bad recipe.
- Builds run the repos' install scripts with network inside Docker; Task 4 Step 1 limits what they reach on this machine, `pgsnap` detects a change, nothing prevents a malicious package from reaching the internet.
- `linux/amd64` recipes run under emulation and can hit the 30-minute limit, so slow amd64-only repos are underrepresented.
